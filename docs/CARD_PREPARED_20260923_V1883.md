# 極薄＋通知 18.8.3

## ユーザーの確定条件

- #イケメングランプリ宵空カップの記事を先頭にする。
- 指定2記事のスキした人と人物単位で統合し、重複者は#の記事を採用する。
- #以外は今日・昨日（日本時間）の新しい記事、なければ固定、固定もなければ最新。
- 最後は `https://note.com/fuku444/n/nb4f6934381e9`（実績の算数）。
- 全件の画像下キャプションに記事投稿者の表示名＋「さん」を付ける。
- 通知用の標準カードを全件作り、公開後は今回の標準カードだけを一括削除する。

## 投稿者・画像の対応

記事APIの key と user.urlname を記事URL・対象者IDと照合する。キャプションにスキ一覧の名前を推測転用しない。name/nicknameが欠けた場合・IDが不一致の場合はエラーにし、空欄のまま完了しない。事前画像は各行のPNGのSHA-256、860×140、順番、重複、最後の実績を読込時にも検証する。

note公開エディターの2026-09-23取得版 `57-2ae1cd5058b7ac1f.js` で、imageノードの `inline*` 内容が `figcaption` に出ることを確認。実際のSchemaを実行し、文字列内容と画像リンクが同一ノードからfigure/anchor/figcaptionに出力されることも確認。本文位置が変化するため、キャプションを入れる処理は画像IDで現在位置を取り直し、後ろの画像から置換する。

## 完成データの連続投入

作成済みPNGをCacheStorageへ保存する。大きい画像データをlocalStorage・本文控えに重複保存しない。スマホ側ではサムネイルの再取得・描画をせず、40枚ずつnoteの正規画像投入処理へ渡す。各組のアップロード、URL、キャプション、下書き保存を確認してから次へ進む。

現在のnote公開エディターのドラッグ＆ドロップが呼ぶ `94928.CwN` の引数と関数本文を照合し、合う場合だけ使用する。合わない場合は既存の「＋→画像」入力経路へ戻す。画像アップロード自体はnoteの処理であり、外部画像を本文へ直接捏造しない。自動公開・自動再読込・ページ移動はしない。

## 初期化の残留

18.8.2は記録に画像IDがあると、そのIDが本文に見つからなくてもsrc＋記事リンクで探さなかった。また進捗記録を失うと同じ記事の本文控えにある画像記録を利用しなかった。

18.8.3では同じ記事の控えも参照し、IDが再生成された画像は保存済みsrc＋リンクが一意に一致するときだけ削除する。重複して特定できない場合や未記録画像、通信中は記録を消さず停止する。元の本文や画像を見た目・サイズだけで削除しない。
