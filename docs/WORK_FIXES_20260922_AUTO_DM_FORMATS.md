## 通知の分類・アイコン・運営への案内

- `stock_photo` が未対応だったため「画像の使用 / image_used」を追加した。保存済み1件も本番で補修済み。
- `embed_note` を一律に引用としていた。行動文に「あなたの記事 が話題です／話題になりました」があるものは「話題 / buzz」へ分類する。指摘の既存行32791がbuzzになったことを本番SELECTで確認。購入通知などのタイトルに「話題」があるだけでは分類を変えない。
- 自動再分類は旧ルールの「その他」と「引用」を対象とし、処理結果の行を直ちに表示へ反映する。保存後に端末のlocalStorageが満杯でも、サーバーの成功を失敗扱いしない。本文もkindも不足する通知は推測で分類せず「その他」に保持する。
- 新着取得のたびに空の画像URLが補完済みアイコンを上書きしていた。既存画像を保持し、新着にも非同期補完を行う。同一の公開actor_urlからの画像補修を本番DBに適用した。取得不能・画像読込失敗時はカテゴリの代替アイコンを表示する。
- マガジン追加などで通知のaction_usersがない場合、確認できる対象URLのクリエイターIDから補完する。記事・マガジンの予約パスを人物IDにしない。
- 分類ルールの更新案内は一般参加者の本人通知から除去。新API `insight-notification-format-reviews` が全参加者の未知kindを集約し、運営者の本人通知画面と運営パネルに表示する。保存情報はkind・件数・初回／最終確認日時・既読日時のみ。他人の本文や名前は返さない。
- 運営者認証は有効なowner session、または本人確認済みss_yrの有効なmember session。クライアントの自己申告roleを信用しない。通常参加者と期限切れセッションは403。既読／未読はサーバー保存。
- これは分類ルールの運営向け案内。参加者が端末のuserscriptを更新するための案内は引き続き必要であり、非表示にしない。

## フィルターと通知パネル

- 設定画面がプロフィールを取得しても、フィルターが使う共有プロフィールキーへ保存していなかった。設定bridgeから名前・ID・画像を保存するよう修正。
- 以前に登録済みで名前が欠ける場合も、noteのクリエイター情報から補完する。取得失敗の再試行は間隔を設ける。
- フィルター対象は、登録した先頭の相手によるマガジン追加／参加通知。スキ・返信・別の相手の通知は隠さない。行の祖先全体を隠さず、通知行単位で反映し、OFFで復元する。
- 「フィルター」と「ON／OFF」はボタン内で2段表示。読み上げラベルは完全な文言を保持する。
- 🔔を開いている間は取得イベントと5秒周期の確認を継続する。最大300件、画面を自動スクロールしない、古い側から保存、保存確認済みの位置だけ進める既存条件を維持。INSIGHTは新着取得を独立して行い、カテゴリ切替で既存の板を空にしない。
- トップの「分析」の下にある重複した「設定」を除去。必要な「インストール／更新あり」と分析画面の正式な設定・更新パネルは維持する。

## DMの取得と保存境界

本番保存メタデータから、実際の取得先が `dm-api.note.com/api/v1/<account UUID>/rooms/<room UUID>/messages`、過去取得が `before=<message UUID>` であることを確認した。旧版のroom判定はこのURL形式を認識していなかった。

1. noteが行う本人のGET通信から、取得URLと必要なヘッダーをメモリ内で学習する。認証ヘッダーは保存しない。通知APIをDM本文として受け取らない。
2. 会話ごとに最新ページを取得し、未保存本文を保存する。保存サーバーが返した確認済みmessage keyだけを保存境界に採用する。
3. 初回はbeforeで過去へ進む。APIが正しい形式の空配列を返したときだけ履歴末尾と確定する。スクロールが動かない／DOMが増えないだけでは全件完了にしない。
4. 2回目以降は最新側から前回保存境界までを追加する。初回の古い履歴が未完なら、保存済みbeforeから続行する。
5. 新着が多い途中で停止した場合も、以前の確定境界を維持し、`pendingHeadKeys` と `headResumeBefore` で未取得の間を飛ばさない。
6. `pagehide`・別画面への移動・非表示は自動一時停止。再表示時に再開する。アカウントが切り替わったら、その取得は停止する。

永続キーはアカウント・会話単位の `mumei_insight_dm_history_v144:<account>:<room>`。`headKeys`、`before`、`complete`、中断した新着区間を保持する。本文の未送信キューはGM永続ストレージへ移し、旧localStorageのキューを一度移行する。ストレージ書込み失敗時は境界を進めない。

1回の自動巡回は最大250ページ。続きがある場合は次の自動巡回で続行し、全履歴を最初から取り直さない。会話一覧も既存取得の全会話キューを処理し、1部屋の取得エラーで後続の部屋を止めない。直接APIが使える場合、部屋HTMLやフレームの余分な再読込を省く。

取得先の学習前は従来のDOM／非表示フレーム補完へ移る。本物のDM通信がブラウザ上で観測できていることが直接API取得の前提。すべてのブラウザ・全会話の実機完了まで確認済みとは扱わない。

## DMの表示と入力

- 「続き読込」などのボタンをなくし、約18pxの1行進捗表示とした。
- 会話では「DM 自動保存中 · 読込／保存」、一覧では「一覧 N人取得 · 自動保存中」。一覧の待機中は消す。
- 実測で入力欄下の空間に収まる場合はそこへ置く。空間が足りない場合は入力欄上へ逃がす。入力中・キーボード・拡大表示中・入力欄未検出時は隠す。
- 進捗表示にpointer-eventsを持たせず、入力欄・送信・既存UIのタップを奪わない。🔔が開いているときはDM表示と巡回を停止する。
- ネットワーク取得は画面をスクロールしない。DOM補完で過去へ進む場合も、入力中の会話スクロールを避ける。本文の下書きは保存対象外。
