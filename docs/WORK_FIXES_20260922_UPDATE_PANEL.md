## 更新パネル

原因：`dashboard-setup.html` と旧v2ページがTOPへ転送するだけになり、分析画面のリンクから更新できなかった。

- `public/dashboard-setup.html` を独立した設定・更新画面として復旧。CSS/JSも同じ機能のファイルへ分離。
- 分析の上部に「ダッシュボードの更新パネルを開く」を表示。準備済みでも小さな設定・更新確認の入口を残す。
- ダッシュボードと本人通知の導入状態を別々に表示する。最新版の参加者に再インストールを要求しない。
- ダッシュボードの利用可否は、このページに実際に起動したuserscriptの属性で確認する。localStorageの過去のバージョン値だけでは起動済みにしない。
- 最新版はno-storeのrelease manifestから取得。通信失敗時は未確認とし、完了を捏造しない。
- インストールは別タブ。戻ったら同じ更新パネルを一度だけ再読込して新しいuserscriptを起動する。失敗時に自動再読込を繰り返さない。
- Android Edge/Firefox、iPhone・iPad Safari、PC Edge/Chrome/Firefox/Opera、Mac Safariの案内を分ける。Android Chrome・Yahoo!などやiOSの別ブラウザには対応ブラウザで開く導線を示す。拡張機能が実際に動いている場合は実動作を優先する。
- 既存拡張機能を入れ直すよう誘導しない。初回導入と「コード文字列になる」時の案内は補足を開いた時に表示。
- 旧v2のURLからもアカウント・戻り先・クエリを引き継ぐ。
- 分析への復帰URLに `insightMode=analysis` を保持する。アプリの現在URLが `#dashboard` だけでも通常パネルへ戻らない。
- データ読み込みは既存pair-start APIを利用し、ログイン中の本人と応答アカウントを照合する。通信中のアカウント切替も停止する。
- 参加者の処理にオーナートークンを混ぜない。noteへのURLには短時間のペアコードだけを渡し、INSIGHTのログイントークンを含めない。
- ダッシュボードだけでも読み込める。本人通知はクロス分析用の独立した更新導線を維持する。
- 既存「データ読み込み」の `auto=1` は本人の明示操作として一度だけ実行する。設定を開く `auto=0` では勝手に読込・画面遷移をしない。

## 通知Storageエラー

画像の省略表示だけでは容量不足か権限制限かは断定できない。コードではjournalとhistoryをnote.comのlocalStorageへ先に書き込んでおり、例外時はGM保存へ到達しない経路を確認した。

- 通知の取得途中データと保存履歴は、拡張機能のGM保存を優先する。note.comの容量・アクセス制限でもGM保存が使える場合は続行できる。
- GM保存が失敗したjournal/historyはlocalStorageへ退避する。双方失敗なら保存完了にせず、日本語の理由を表示する。
- 旧localStorageの未送信データは読んで移行する。GM保存を確認した自分の同一キーだけを除去する。noteのデータ、ログイン、他人の記録を一括削除しない。
- 両方にコピーがある時はrevisionの新しいものを採用し、削除できなかった古いコピーで保存位置を巻き戻さない。
- journal/historyの既存フィールドはトップレベルに維持する。追加属性は `__mumeiDurable:1` と `revision`。完了journalは `schema:0, __mumeiDeleted:true` の記録とし、現在コードではnullとして扱い、古いコードでも新しい窓の作成へ進める。既存データを互換性のないvalueラッパーに閉じ込めない。
- outboxは従来の配列のまま保持。outbox・チェックポイントのGM保存失敗を握りつぶさず停止する。
- サーバーの保存確認後にだけ保存位置を進める。停止・通信失敗からの再開、最大300件、下から上、画面の自動スクロールなしを維持する。
- DM・通知パネル制御・分類・DBは今回のStorage修正で変更しない。
