## 通知：取得・保存・表示を分離

- Network Readerは `/api/v3/notices` のルート通知だけを読む。通常チャットの `extractDirectNotices` を維持し、関連記事・マガジン説明などを再混入させない。
- Readerの自動入口をAPIに統一。DOM自動スクロール保存は行わない。
- アカウント別の `mumei_notification_window_v360:<noteId>` に取得中／未送信通知を先に保持する。localStorageとGMへ保存する。
- 初回は最大300件を収集し、古い順に20件単位で送る。**順序保証のため、初回収集が終わる前の「新しい通知の先行保存」は行わない。保存済みの板はその間も先に表示する。**
- 保存完了応答の `confirmedClientSignatures` を照合してから未送信分を取り除く。停止直前に通信中だった塊は応答確認後に境界を進める。応答不明なら次回に再送し、サーバーで重複排除する。
- 次回は未完了journalを優先。その後は保存済み署名までの差分。前回先頭通知が消えても、ほかの確認済み通知で止まる。
- 履歴の境界もGMだけでなくlocalStorageへ保持。全件完了をGMの一時的な読取失敗で忘れない。
- 可視の全履歴Feedとは別に `action: recent` を追加。最大300行の差分を返し、全履歴集計が終わるまで待たせない。再分類更新も対象にする。
- INSIGHTはアカウント別の保存済み板を先に表示。本文を人物アイコン通信より先に描画。カテゴリ先読み、最大2,000行の端末保持、メモリのカテゴリキャッシュを利用する。
- 保存状態の変更通知で新着取得を起動。非対応環境では1.5秒間隔の確認で補完する。「即時」は保存応答と通信時間を含み、無通信でサーバーの変化を知れるという意味ではない。
- 全履歴Feedは30秒キャッシュ＋保存時刻の差分を利用。毎回約1.7万行を読んでいた経路を減らす。

## 分類と再分類

- 自動再分類は「その他・未分類」の未処理行に絞る。手動の全体確認は別。100件カーソル、8件並列、カーソル保存、同一カーソル検知、停止・タイムアウトを用いる。
- 同じ分類器で判別できない通知を無限に処理しない。原文はその他に残す。分類器更新／新規通知のときに再試行する。
- 通常チャットが隔離した `meta.noise_reason=non-notification-api-capture` を維持する。数字＋期限だけの誤取得も原文を残してcapture_noiseへ分離する。
- 古いDBトリガーがEdge Functionの分類をその他へ戻していた。今回のmigrationは最終段のトリガーを追加し、V25が保存した `meta.classified_type` を許可リストで受け入れる。既存の本文・会員データ・RLSは変更しない。
- `qa_answer`、購入記事更新を含む構造化kindを分類する。未知kindは未読の「カテゴリ更新」案内にし、既読状態をアカウント別に保持する。

## DM：今回実装した修正と未確認点

- 2人を処理して3人進む旧不具合に加え、失敗を全件完了としていた処理を修正。全相手を順番に巡回し、確認済みの相手は中断からの再開時に飛ばす。
- noteの他画面からDMへ通常遷移しても起動するよう、専用ツールのmatchをnote全体へ拡張。実処理はDM経路に限定する。
- メッセージ本文のdiv候補を増やし、複数吹き出しの親を一つの本文として扱わない。相対時刻が変わるたび別キーになる不具合を修正。
- DOMと通信取得それぞれに未送信キューを保持。`confirmedMessageKeys` の確認前に削除しない。0件・本文未検出・タイムアウトを完了としない。
- 親画面と内側タブの連動を維持し、他項目へ移動したらDMコンポーネント自体を外す。
- 設定・状態を明確な押せる行にし、本文読込・保存・失敗を表示する。相手を切り替えた後の古い本文応答は採用しない。
- **本物のnote DMのDOMはこの環境で取得できていない。実機で20人分の本文取得に成功したとは報告しない。** 再現fixtureの成功は本文取得経路の確認に留まる。
- 次に0件が続いた場合は、端末のDM設定・状態の `lastError`／失敗相手／読込件数を確認する。`DM_CONVERSATION_NOT_FOUND`なら実DOM候補、`DM_MESSAGE_BODY_NOT_FOUND`なら本文構造、`DM_SAVE_UNCONFIRMED`なら保存応答、`TIMEOUT`ならフレームの読み込みを優先して調べる。
- 仮想化された相手一覧や長い本文、APIとDOMで同一本文を二重に取得する場合は実データで要確認。一覧のプレビューを本物の全本文として水増ししない。

## フォロー履歴・解除調査の仕様

| 項目 | 動作 |
|---|---|
| 最新1,000人 | 最新照合に含まれる人物をsource_rank順、最大1,000人。フォロー／フォロワーの両方向に対応 |
| 過去から1,000人 | INSIGHTの初回保存日時が古い順、最大1,000人。現在枠外の人物も含む。note上でフォローを始めた真の日付とは区別する |
| 解除・関係終了を調査 | 保存した減少記録を名前・note ID・日付・方向で検索 |
| 人物別「調査」 | 初回／最終確認、両方向の状態、最大100件の変化と照合根拠を表示 |
| 全件照合の減少 | 「関係終了を検知（原因不明）」として表示。解除・退会・ブロック等の原因は断定しない |
| 最新枠だけの消失 | 解除した人物とは断定しない。過去の推定記録は候補・未確定と表示 |
| 総数だけの減少 | 人物を推測で割り当てず、不明人数として保持 |

本番確認時、保存済みフォロワー1,219人（最新枠1,000＋枠外219）。過去表示はこの既存保存を使う。**保存を始める前の人物、noteが返さない範囲を復元したという意味ではない。** 今回、既存の `insight_relations.active=false` は最新枠からの消失を含むため、解除確定の根拠として使わない。

- 線・棒・円の立体感は陰影・グラデーションで付け、長さ・角度・割合は変形しない。
- 通常チャットがmainへ保存して本番未反映だった `insight-dashboard-data` の公式日別系列による比較も今回配備する。
