# 2.9.4：区切り線があるのに再開できない停止の修正

変更前は **2.9.3 / `9a2f79d7e756f10bc5ccd9c08de6bf634fe3f49e`**。配布元とmainの一致を確認してから作業した。利用者の画面では、完成した画像と区切り線が見える一方で「区切り線の保存記録が未確定」となっていた。利用者の画像や実名をこのリポジトリには追加していない。

## 調査した既存処理

画像の正規アップロード完了・リンクとキャプションの設定・画像の途中記録を終えてから、直後へ区切り線を挿入する。画像が完成した後の失敗では画像を再送しない。再開時は同じ下書き・作成単位・画像・人物行を照合し、既知の人物／記事／タグ不一致も先に確認する。

2.9.3は線の所有記録を作る前に、トランザクションで予定した本文全体と実際の本文全体の完全一致を必須にしていた。note側の追加処理で属性や末尾段落などが整えられると、目的の画像と線が存在しても挿入未確定となる。この経路を実ProseMirrorの模擬環境で再現する。スマートフォンの内部状態を取得できたという意味ではない。

## 今回の変更

- 要求したトランザクションの文書と現在の文書が同じ実体である場合は、その確定済みの結果を利用する。単に同じJSONに見える別の文書を、この短縮経路では合格にしない。note側で文書が変わった場合だけ、対象画像の識別情報・リンク・キャプションと画像直後の局所構造を確認する。既存の連続した線が、新しい線の後に同じ順序で残っていることも確かめる。本文の無関係な場所の正規化だけで停止しない。線の実際の属性を記録する。
- 以前に記録した所有済みの線が移動・変更されていたら、同じ場所に二本目を足さず保留する。作成済み画像の再アップロードは行わない。
- 2.9.3の古い途中記録と、その画像直後の線だけが残るケースでは、同じ下書き・作成単位・記事・人物行・重複していない実画像・最後の作成画像との対応を確認してから、その線の後へ続ける。native HRの属性だけが変わった場合も、同じ線の型・leaf構造であることを確認する。代替段落は予定した文字列・構造の完全一致が必要。
- 古い途中記録から線を保持する場合、その線の所有を確認済みにはしない。`coreExternalDividerRecords`へ、所有未確認・実際の線のJSON・根拠を記録する。追加の線は挿入しない。検査も「線の存在」と「所有・属性の由来は材料不足」を分ける。**この線は「今回分を全削除」でも残す。** 手動の線を誤って消さないためである。
- 新しい挿入失敗の記録はversion 2として区別し、古い途中記録向けの復旧へ無条件に回さない。新しい失敗・既知の人物／記事／タグ不一致・保存失敗は引き続き保留する。
- 明示的な「今回分の表示を整える」でも、上記の古い途中記録を復旧する場合は、線の追加ではなく所有未確認の対応記録だけを復旧する。プレビューを開く・更新を読み込むだけでは本文を変更しない。古いプレビュー・変更された所有済み／所有未確認の線は適用しない。
- 保存記録の最初のJSON変換は残し、正規化済みのバックアップ用コンテナだけを独立して再帰複製する。文字列などの不変値は共有しても、オブジェクト・配列は一つも共有しない。`__proto__`は安全な自身のデータ属性として保持し、深さ制限や例外では従来のJSON.parseへ戻す。複製はメモリ公開・localStorage呼び出しより前に完了する。保存形式・キー・書き込み件数・キュー・失敗時の保護は変更しない。
- 通常処理へ追加の通信・人工的な待機・全件の取り直しを加えない。入力、設定、キャッシュ、進捗の保存キーを変更しない。
