# 極薄サムネイル 2.9.0：品質検査の記録専用導入

## 基準と公開範囲

変更前は **2.8.0 / e2e1b3f8a4b37721f3ddc59b4fd7abc4c1419b1b**。
更新案内・実配布・生成元・生成手順を現物確認した。[既存チェックのモード別記録](BASELINE_20261030.md)を参照。

今回は仕様書9の**結果記録だけ行う段階**。追加検査からの自動保留・自動修正は有効にしない。既存の停止、候補採用・除外、画像・カードの順序、保存成功の条件は変更しない。追加検査の未確認事項を合格にしない。既存の安全停止を無効化する機能はない。

スキ履歴の初期200人・人物重複なし・200種、1〜1500人指定/全数、通常のURL/マガジン/タグ、最初/固定→最新/最新、初投稿・自己紹介/ワーママ/育児日記、参加者126人と記事なしの既存経路を保持する。画像寸法860×140、元のPNG、描画・文字サイズ・本文/キャプション・改行処理・見出し・区切りは変更しない。

購入記事紹介の欄と実装は一般の極薄配布から外す。独立した購入記事紹介のスクリプトやその保存データを削除する処理は入れない。そちらを別にインストール済みの場合、ブラウザーのユーザースクリプト一覧で無効にする必要がある。

INSIGHT本体、insight-guide、MUUMEI、ゲーム、DB、認証、配信設定は変更対象外。追加サーバー・AI API・OCR・画像送信はない。極薄からINSIGHT本体を起動しない。

## 追加した検査と根拠

| 観測箇所 | 根拠 | 判定の限界 |
|---|---|---|
| 対象/記事/プロフィール | 選択されたアカウント、変換前の生記事の投稿者・記事ID・元URL、詳細APIの投稿者/記事ID、プロフィールAPIのurlname | 無い識別情報は照合材料不足。名前やテーマは人物識別に使わない |
| 取得→生成→画像リンク | 取得時の対応記録、生成FileのWeakMap対応、実画像ノードのリンク/キャプション | 違うFile/人物/URLを渡す例を検出。画像からの本人認識ではない |
| 画像内の名前/文字枠 | 実際のfillText呼び出しと文字の指紋、実TextMetrics、当該canvas寸法 | OCRではない。既存の名前省略は確認候補。変換/文字境界が測れない場合は未確認 |
| アイコン/記事画像 | 同じアカウントの取得データに採用URLがあるか | 原画像の絵柄による人物照合や画像内容の正しさは保証しない |
| 紹介ブロック/区切り | 当該insertActivityAtの挿入結果と元文字列、この画像直後の区切りノード | 隣接する他の段落から人物を推測しない。全エディターを追加走査しない |
| 改行/本文 | 元の手動改行位置、既存レイアウトが生成した行と幅、文字保持、英数字の行境界 | 自然な折り返しは誤りにしない。意図的な英単語途中の手動改行も区別。貼付先の見え方は未検査 |
| 通知カード | 既存処理が照合・記録した直後のembedのsrcと対象記事ID/アカウント | 既存のpending/重複/所有記録/停止条件を変更しない |
| 下書き保存 | 元の保存処理の肯定的結果、失敗/未確認結果 | voidや要求済みを成功にしない。保存再試行を追加しない |

判定は確認済み（その検査の範囲）/確認候補/明確な不一致/照合材料不足/検査失敗/未実施。異なる話題、同名、装飾、改名、敬称を理由に人物の誤りとは判定しない。元の表示名を短縮・装飾削除する処理を追加しない。キャプチャ・本文に検査結果や新しい名前を足さない。

検査関数は判定と根拠を返す。記録・取得元の紐付けは独立アダプターが担当し、元の入力オブジェクトを変更しない。生成・取得・native挿入/保存の戻り値を維持する。描画観測は元のfillTextを同じ引数で1回呼ぶ。既存画像/本文の書き換え、追加通信・待機・再取得・並列数変更はしない。

`Aの画像/名前 → 区切り → Bのプロフィール` は正常な別ブロックとして検証した。上下の文章を同一人物だと推測せず、不一致にしない。画像内とキャプションの元の名前に、検査用の名前を二重追加しない。

## 表示・保存・無効化

既存パネルの同じ見出し行に「検査記録」を置く。候補/明確な不一致が記録されたら「検査候補」/「検査相違」と表示し、押した時だけ詳細を重ねて開く。通常時のパネルに行を追加せず、本文には表示しない。確認ボタンや常時ダイアログは増やさない。

検査の例外や1回30ms超過は「検査失敗」を記録し、以後の追加検査を無効にする。元の例外を握りつぶしたり、既存の安全停止を解除したりしない。停止・修正を導入する次の段階には、別途検証が必要。

詳細内の「追加検査を無効化」で独立してOFFにできる。OFFでも既存入力・設定・キャッシュ・進捗・画像・リンク・照合根拠は消さない。ログは元のrun/GMバックアップと別のキー。元の進捗には短い参照IDだけを追加し、大きな照合記録を毎回再保存しない。

根拠ログは直近160記録、取得元の小さな記録は最大1024件、保持する下書きは直近3つ。表示の件数は今回の作成分での検査回数であり、合格した人数ではない。新しい作成を始めるたびに今回分の判定を分け、以前の作成分の結果を流用しない。保存済みの同じ作成分を再開するときは同じ検査記録を継続する。以前の根拠は保持上限の範囲で残す。大きな全数処理などで根拠が保持上限から外れた場合は照合材料不足に戻し、取り直しを強制しない。プロフィール全文や画像を検査用に二重保存せず、表示名/本文の対応には非暗号学的な指紋を使う。これは身元保証や署名ではない。URLの検索パラメーター・fragment・userinfoを記録せず、Cookie/認証情報は読まない。利用者のスクリーンショットや購入記事データは公開fixtureに含めていない。

## 検証

### 実行した内容

実配布の2つの識別子で同一の本文・ガード・更新URLを確認。基準コミットの配布物と現在の配布物を、そのまま匿名の模擬環境で実行して比較した。

- 人数2→7→1→4、対象アカウント、スキ履歴→タグ→マガジン→スキ履歴を連続して変更し、その回の全件を検査することを確認。同じ下書きでの次の作成分と再開も区別し、前の相違判定を今回の判定に混ぜない。ハロウィーンの使用は必須ではない。
- 実ProseMirrorで作成したノード構造、本文全文、リンク、キャプション、順序、待機値、リクエスト列を比較。
- 実canvas/PNGでスキ履歴の少数/200人全デザイン、参加者126人＋実績、通常3取得元×3記事選択を比較。生成されたPNGのSHA-256が前後で一致。
- 自己紹介/初投稿の現行フロー、ワーママ、育児日記、全数、逆順で完了する並列取得、記事なし・アイコンなし・確認済みサムネイルなしを比較。
- 意図的な投稿者/記事ID/生成Fileの入れ違い、同名別アカウント、改名・絵文字・敬称・話題違いを検査。
- 区切りの上下に別人、名前二重追加なし、手動改行/自然な折り返し/単語境界/文字枠外の候補を確認。
- native画像失敗の再試行、画像/カード一時停止・再開、保存失敗/未確認、通知カードtap位置/削除、既存ノード保持を確認。
- 追加検査の例外・時間予算超過・OFF・ログ保持上限・再読み込み、現行の途中記録を旧版が継続できることを確認。
- 不一致をすべて確認済みにする改変を検査器に入れ、負のfixtureの検証が実際にAssertionErrorになることも確認。固定PASSではない。

結果：**546件中539成功、7失敗、skip 0**。新規41件はすべて成功。残る7件は変更前から存在する `tests/profile-card-paster-v1.test.mjs` の旧v1.7.1向け固定仕様テストで、同じ7件の失敗を変更前に再現した。今回、その古い期待値を変更して結果を緑にする対応はしていない。更新版数を期待する4つの現行テストのみ2.9.0に更新。

実行コマンド（各*_TEST_MODULEはそのパッケージのインストール先）：

```sh
node scripts/build-profile-card-standalone.mjs
PM_MODEL_TEST_MODULE=.../prosemirror-model \
PM_STATE_TEST_MODULE=.../prosemirror-state \
CANVAS_TEST_MODULE=.../@napi-rs/canvas \
KATEX_TEST_MODULE=.../katex \
node --test --test-reporter=tap tests/profile-card-*.test.mjs
```

PM/canvasの任意依存や基準コミットが無い環境では比較テストを明示的にskipする。この作業での実行は上記依存と基準を用意し、skipなしで実施した。基準の配布ファイルは `QUALITY_BASELINE_SCRIPT` でも指定できる。

### 速度

最初の試作は、根拠を元の進捗に入れていたため目標を超え、採用しなかった。取得元の記録を独立させて、同じ入力200人・固定乱数/内部時計・同じキャッシュ・同じ実行環境（経過時間は外側のperformance.nowで実測）で再測定した。元の50ms待機も実際に実行し、追加検査の待機は0。両版を1回ずつ予熱後、順序を交互にして各5回測定。

最終測定の中央値は **2.8.0: 13.839秒 → 2.9.0: 14.211秒（+2.68%）**。模擬環境での5%目標内。各回の値と配布物のハッシュは `BENCHMARK_20261030.json` に記録した。これは**同じ管理環境のNode＋実PM/canvas、noteの通信/画像アップロード/保存能力を模擬した測定**。スマホや実際のnoteの所要時間ではない。`node scripts/benchmark-profile-card-quality.mjs 5` で再現できる。

## 未確認と次の段階

コード確認、模擬動作、実機を混同しない。**Android/Edge実機の画面、操作感、5%以内の速度目標、実noteの通信/アップロード/保存は未確認**。本番記事での貼付・削除・公開テストは実行していない。画像内の見た目の重なり、note側の表示幅による実際の欠け、画像の人物認識も未検査と表示する。

今回公開する範囲は記録専用まで。検証された識別情報の不一致による新しい自動保留は、この版では導入しない。曖昧な意味・改行の好みを停止条件にする設計はない。全品質の保証やスマホ実測の達成としては扱わない。
