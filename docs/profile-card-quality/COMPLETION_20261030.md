# 極薄サムネイル 2.9.1：毎回の検査と、明確な不一致の保留

## 今回の完了範囲

直前の変更前は **2.9.0 / `3f34047053576c91c2a6ea284433b077f6bf83bf`**。記録専用で止めていた追加検査を、検証できた識別情報の不一致だけ実際の貼付前に保留するところまで実装した。

元の正常動作との比較基準は引き続き **2.8.0 / `e2e1b3f8a4b37721f3ddc59b4fd7abc4c1419b1b`**。[既存チェックのモード別調査](BASELINE_20261030.md)と[記録専用段階の実装・検証](IMPLEMENTATION_20261030.md)は履歴として残している。

人物・記事・件数を固定しない。スキ履歴、記事URL、マガジン、タグ、初投稿/自己紹介、ワーママ、育児日記、各件数/全数の生成・貼付・再開で、その回の対象を検査する。ハロウィーンは既存の任意モードであり、新しい検査の使用条件ではない。通常の200人・200種、他モードの件数設定や表示は元のまま。購入紹介の操作欄は前版で一般の極薄から外しており、復活させていない。

INSIGHT本体・DB・認証・insight-guide・MUUMEI・ゲーム・配信設定は変更しない。新規サーバー・有料API・OCR・外部への画像送信は追加していない。

## 何を保留し、何では止めないか

| 判定材料 | 動作 |
|---|---|
| 選択したアカウントと、生記事の投稿者・プロフィールのIDが明確に異なる | 対象を保留 |
| 選択した記事IDと、取得した記事・元URLの有効な記事IDが異なる | 対象を保留 |
| 現在の行のアカウント/記事と、そのFileに記録された生成元のアカウント/記事が異なる | 生成画像を貼らず保留 |
| プロフィールや投稿者のIDが無い、取得元の対応記録が無い、不正形式のIDしか無い | 照合材料不足。追加検査を理由に停止/合格にしない |
| 表示名変更、装飾・敬称、同じ人の異なる話題、任意画像の未設定 | それだけでは保留しない |
| 手動改行、自然な折り返し、単語境界・文字枠の確認候補 | 記録・表示だけ。自動修正/強制停止しない |
| 検査の例外・時間予算超過・OFF | 新しい追加検査は無効化できる。既存の安全停止と既知の保留は維持 |

有効なID同士の矛盾だけを機械的な保留条件にした。名前や話題の似かよりは使わない。`note.com` と `www.note.com`、末尾スラッシュ等の見た目の違いは、URL中のアカウントと記事IDが同じなら矛盾にしない。

画像内の名前は実際の描画呼び出しを観測し、元の描画・キャプション・紹介文に検査用の名前を足さない。`Aさんの画像/名前 → 区切り → Bさんの紹介` は正常。隣の文章から人物を推測しない。

## 保留・再開とデータ保全

取得段階では矛盾を記録するだけにし、そこで例外を投げて人物を候補除外する経路には入れない。実際の保留は見出し・プロフィール・画像・通知用URLを書き込む前に行う。画像取得失敗用の `ASSET_UNAVAILABLE` とは別の `QUALITY_HOLD` を使い、除外/補充/別人や別記事への差し替えは行わない。

coreの見出しを先に挿入していた経路は、元から1回実行していた画像生成をその見出し挿入より前に置いた。画像を余分に生成せず、最終出力の順序・大きさ・デザイン・改行・区切り・待機は維持する。保留した人の見出しだけ残すことも避ける。

確定した矛盾は当該行の小さな `qualitySourceIssue` と、元の進捗の `qualityHold` に保存する。local/GMバックアップは既存の保存経路を使う。通常の正しい行に大きな証拠データは追加しない。検査ログ160件/取得元キャッシュ1024件の上限を超えても、既知の矛盾は消えない。OFF・例外・API機能の欠落・再読み込み・初回ボタンの押し直しでも、進捗に残る保留を無視しない。両保存先が失敗した場合もその場のメモリーと本文を保持して止め、保存できたとは表示しない。

保留した分は完了扱いにしない。対応する完了時刻も残さない。先に貼れた人の画像・本文・順序と、既存の未確定カード要求は保持する。通知カードを手動で追加して既存の変換復旧が拾える状態になっても、保留を飛び越えて完了させない。すでに作ったカードの対応も、再開/完了確認前に確認する。

通常操作に確認ダイアログや新しい入力は増やさない。保留時も元の再開操作を使う。

- **未貼付データの識別情報の保留**：元の同じ記事ID・アカウントの詳細とプロフィールだけを取り直す。一致と必要な本文材料が揃ったときだけ、未貼付の一行のデータを更新し、同じ位置から続ける。記事選択・URL・順序・デザイン・件数は変更しない。必要なサムネイルの元のOG取得fallbackは、この一件の再確認時に限り使う。
- **Fileの取り違えの保留**：元の行の画像を生成し直し、実際に一致するFileの対応が確認できてから再開する。記事/プロフィールの再取得はしない。
- **材料不足や応答の矛盾が残る場合**：保留を維持する。OFFで強制解除しない。
- **画像をすでに貼った行、旧版の未完了プロフィール等との対応が未確認の場合**：既存の画像や本文を自動で書き換えない。プロフィールを更新すると所有済みの紹介が古くなる場合も保留を維持する。元の今回分を作り直す必要がある場合は、利用者が既存の「今回分を全削除」/「最初に戻る」を選ぶ。対象外の本文や画像は削除しない。

記録専用2.9.0で記録済みだった有効なIDの矛盾は、同じ作成分・行に紐づくものだけ進捗へ移す。新しい対象選択に前の判定を流用しない。検証した再取得/再生成と進捗保存が済んだものだけ解除し、以前の証拠は「解決済み」として残す。保存失敗や作成先の切替中には、元の行と保留を保持する。

## 画面とプライバシー

既存の見出し行の小さな「品質検査」ボタンを使う。「検査保留」になったときも詳細は押した場合だけ開く。パネルに常時の新しい行を増やさず、本文には表示しない。

既存の入力・設定・キャッシュ・進捗の初期化や再ログインは要求しない。追加検査は詳細からOFFにできるが、記録や既知の保留は削除しない。別アプリへの移動や再入力は不要。

新たに保存する確定矛盾はIDと理由だけ。プロフィール全文や画像を検査のために二重保存しない。認証・Cookie・トークンをログに入れない。公開fixtureは架空の人物・記事であり、利用者の画像・スクリーンショット・購入リストを追加していない。

## 速度

同じ管理環境、同じ入力200人、同じキャッシュ、固定乱数、実PM/canvas、元の50ms待機を実行し、1回ずつ予熱後に前後各5回を交互に測定した。今回は内部時計も実時計とし、30msの検査時間予算が実際に働く条件で測定した。検査が故障して無効になった測定は採用しない。

中央値：**基準2.8.0 14.212秒 → 2.9.1 14.613秒（+2.82%）**。模擬環境での5%目標内。通常経路の追加通信・待機・全件取り直しは0。元の取得並列数、50msの画像間隔、600msから処理時間を引くカード間隔、10件ごとの2500ms待機はそのまま。

測定値・条件・配布物のハッシュは `BENCHMARK_291_20261030.json`。`node scripts/benchmark-profile-card-quality.mjs 5` で再現する。noteの通信・アップロード・保存能力は模擬であり、スマホ実測の5%達成と読み替えない。
